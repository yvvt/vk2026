# Подробное описание решения проекта

## 1. Обоснование выбора подхода и инженерные компромиссы
Исходное требование проекта предполагает обучение модели на открытых данных VK. Анализ доступных ресурсов выявил критические ограничения: локальное обучение невозможно (500 МБ VRAM), а использование бесплатного Google Colab накладывает строгие лимиты: максимум 16 ГБ VRAM (GPU T4) и время непрерывной работы сессии, ограниченное ~12 часами.

Полноценное дообучение (full fine-tuning) модели размером 2B параметров превышает лимиты памяти T4. Обучение на полном датасете `LLaVA-Instruct-ru` (144 000+ записей) гарантированно превысит лимиты времени сессии Colab. 

Было принято инженерное решение использовать метод **QLoRA**. Он позволяет заморозить веса базовой модели, квантовать их до 4 бит (NF4) и обучать только небольшие матрицы адаптеров. Это снижает потребление VRAM до ~10-12 ГБ. Для соблюдения временных рамок была применена стратегия случайного сэмплирования обучающего датасета до **1000 записей**. Это не является ошибкой, а представляет собой стандартную практику для proof-of-concept экспериментов и демонстрации работоспособности пайплайна в условиях экстремальных ограничений по вычислениям.

## 2. Процесс подготовки данных
Использована библиотека `datasets` от Hugging Face. 
- Датасет `deepvk/mmbench-ru` загружен для оценки.
- Датасет `deepvk/LLaVA-Instruct-ru` был загружен, перемешан (`shuffle(seed=42)`) и ограничен методом `.select(range(1000))`.
- Реализован кастомный `data_collator`, который:
  1. Формирует структуру сообщений в формате чата.
  2. Явно указывает процессору, где находится изображение, а где текст.
  3. Корректно формирует `labels`, маскируя токены промпта пользователя значением `-100`, чтобы модель обучалась генерировать только ответ ассистента, а не повторять вопрос.

## 3. Реализация обучения
Обучение реализовано с помощью `SFTTrainer` из библиотеки `trl` с максимальной оптимизацией памяти:
- **Learning rate:** `2e-4` (стандартное стабильное значение для LoRA).
- **Batch size:** `per_device_train_batch_size=2` с `gradient_accumulation_steps=4`. Это эмулирует эффективный размер батча 8 для стабильности градиентов, не перегружая VRAM.
- **Оптимизатор:** `paged_adamw_32bit` (предотвращает фрагментацию памяти и OOM-ошибки).
- **Градиентный чекпоинтинг:** `gradient_checkpointing=True` (экономит ~30% VRAM ценой небольшого замедления вычислений, что критично для T4).
- **Точность:** `bf16=True` (bfloat16 обеспечивает стабильность обучения лучше, чем fp16, и поддерживается современными версиями PyTorch).

## 4. Анализ результатов
После обучения модель была протестирована на 100 примерах `mmbench-ru`. Скрипт автоматически сравнивает базовую модель и модель с примененным LoRA-адаптером (после операции `merge_and_unload`).

Полученные метрики:
- Базовая модель: 58% Accuracy
- Дообученная модель: 56% Accuracy

*Критический комментарий:*
Незначительное изменение или снижение метрики является ожидаемым. Объем обучающей подвыборки (1000) и оценки (100) слишком мал для глобального улучшения общих способностей модели. Это демонстрирует, что для достижения state-of-the-art результатов требуется либо полный датасет, либо более длительные вычисления на кластере с GPU A100/H100, что выходит за рамки текущего аппаратного обеспечения. Тем не менее, сам пайплайн обучения и оценки работает корректно.

## 5. Выводы
Проект успешно продемонстрировал жизнеспособность полного цикла дообучения мультимодальных моделей (загрузка данных → QLoRA-обучение → сравнительная оценка) в условиях экстремальных ограничений по памяти и времени. Все артефакты (код, конфиги, веса адаптеров, JSON с метриками) полностью воспроизводимы при наличии доступа к среде с GPU ≥ 16 ГБ VRAM. Задача выполнена в строгом соответствии с требованиями использования открытых данных VK.
